# Agent Note: 移动端设置使用两级导航

Status: implemented

[English](2026-08-26-mobile-settings-navigation.md) | 中文

## Problem

设置对话框在所有视口宽度下都把 188px 的设置分类导航和当前页面并排显示。在手机上，对话框宽度只有视口宽度，导航会占用大部分可用空间，设置控件只能挤在剩余的一列中。桌面端的双栏布局仍然有用，必须继续同时显示导航和内容。

手机导航还需要明确的上一级。选择设置分类只是查看操作，不是设置变更；平台 Back 手势必须返回分类列表，而不能关闭对话框或修改任何设置。

## Decision

低于 640px 时，设置对话框是占满视口的单栏界面。打开设置首先显示完整分类列表。选择一行后，两栏仍保持挂载，但所选设置页占满视口宽度，导航栏裁剪为零宽；返回列表时导航重新占满宽度，内容栏裁剪为零宽，因此分类页面内部的表单状态得以保留。更宽的视口继续使用同时显示两栏的居中面板。

设置壳在当前浏览器 History 状态中保留所有无关字段，并在 `__dshSettingsView` 下压入列表和内容条目。这包括由[移动端会话导航](2026-08-26-mobile-session-navigation.zh.md)拥有的 `__dshMobileView`。`popstate` 将内容子条目映射回分类列表，并在回到前一个非 Settings 条目时关闭对话框。关闭、遮罩和 Escape 操作从列表退出一个条目，从设置页退出两个条目。

首次使用引导的 `openSection(id)` 会先创建列表父级，再创建所请求的内容子级，因此无论用户从侧边栏还是引导进入设置，平台 Back 的结果都相同。响应式目的地和 History 集成仍是 `ui-settings-general` 内部的组件查看状态；各设置注册者继续拥有自己的字段和变更逻辑，slot 与 settings service 接口均不改变。

## Alternatives considered

**缩窄导航栏但继续并排显示两栏。** 仅显示图标或缩短标签能收回一部分宽度，但内容仍无法使用完整手机宽度，而且分类更难辨认。

**使用顶部选择器或横向标签替代分类栏。** 选择器会隐藏可用分类；随着插件增加分类，标签要么横向滚动，要么被截断。两者都会为与会话相同的列表到详情关系引入另一套移动端导航语义。

**把分类导航渲染为覆盖设置页的抽屉。** 抽屉可以保留全宽内容，但会把分类列表变成临时浮层而不是上一级页面，使平台 Back 依赖额外的展开状态，而不是浏览器 History 栈。

## Consequences

- 手机设置将完整视口用于分类列表或一个设置页；非活动子树保持挂载，但在视觉和无障碍树中隐藏。
- 两个手机层级都有可见关闭控件。History 改变页面后，焦点会跟随该控件。
- Settings 会增加同 URL History 条目。其他应用内 History 所有者必须保留外部状态键，Settings 也遵守这一要求。
- CSS 与 JavaScript 以 640px 阈值作为源码级不变量；修改断点时必须同时更新两处声明。
- 桌面端的打开、分类选择、Escape、遮罩关闭、面板尺寸以及同时显示导航与内容的行为保持不变。

## Testing

`settings-root.client.spec.tsx` 覆盖手机断点识别、初始列表状态、外部 History 字段保留、进入分类、Back/Forward 投影、关闭层级退出、可见页面无障碍状态及首次使用引导入口。`apps/web/tests/settings-chrome.e2e.ts` 在 390×844 的 Chromium 中启动正式 Web 组合，记录 `390/0` 与 `0/390` 栏宽，捕获本地化分类列表，并驱动浏览器 Back 与 Forward。
